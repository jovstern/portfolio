## Experiment: `experimental.inlineCss` (owner-approved)

**Setup.** I added `experimental: { inlineCss: true }` to `next.config.ts`, rebuilt with
`CONTENT_FIXTURES=1` and served the build on the same port. I then ran the same 9 mobile and
3 desktop runs. The flag replaces the 6.8 kB stylesheet `<link>` with a `<style>` tag. Per the
Next docs, the CSS is also repeated in the RSC payload of the same document.

**Mobile LCP runs with inlineCss (ms):**

- `/`: 2363, 2412, 2414, 2340, 1804, 2412, 2413, 1805, 2415
- `/projects/portfolio`: 2490, 2490, 2488, 2488, 2487, 2491, 2486, 2334, 2338

**Why it is slower.** Removing one 6.8 kB render-blocking request costs the HTML document
about 15 kB gzip, because the CSS is shipped twice (in `<style>` and in the RSC payload).

- On Lighthouse's simulated mobile link, a document of about 24 kB no longer fits the first
  TCP congestion window (about 14.6 kB). It needs another round trip before the first byte of
  CSS is parsed. That pushes FCP back about 35 ms.
- The bigger document also delays the parse and the script discovery that LCP depends on.
- The fast LCP mode that half the baseline runs hit (about 1655 ms) all but disappears.

**Decision: rejected.** It fails the owner's rule: the median is not ≤ 1.8 s on either route,
and LCP, FCP, Perf and desktop LCP all regress. `next.config.ts` is reverted, so the working
tree matches HEAD. No ADR was written: ADR 0002 was conditional on keeping the flag. Raw
reports are in `.metrics/post/inline-*.json`.

## Misses and resolution

### 1. Mobile LCP: 2179 ms on `/`, 2255 ms on `/projects/portfolio` (budget 1800 ms). Accepted for M1 by Yoav

**Accepted by Yoav on 2026-10-25** for M1, with the cause written down: Lighthouse's simulated
mobile runs land in two groups. In the slow group (6 of 9 runs), React's runtime and the Next
router execute before first paint and are counted in LCP. The floor with JS blocked is about
1.6 s, and real throttled Chrome measured 1.45–1.48 s. `browserslist` (no effect) and
`experimental.inlineCss` (worse) were tried and reverted.
**Follow-up:** re-measure on the Vercel preview with PageSpeed Insights in M3, and check real-user
LCP in Speed Insights after launch.

**Cause.** This is unchanged from the first pass and confirmed again. The simulated LCP has
two modes, about 1655 ms or about 2180–2350 ms, while FCP stays at 754 ms in every run.

- The slow mode happens when the framework JS is evaluated before the first paint. The JS
  is `20box33a0_n53.js` (react-dom, 71.9 kB gzip) and `3l_qmp-61z4yc.js` (Next router,
  46.5 kB gzip). In those runs Lantern puts the JS download and its 4×-CPU execution on the
  LCP path.
- With all chunk JS blocked, LCP is 1578–1655 ms.
- Localhost delivers every resource in under 35 ms, which creates the race; a real network
  delivers the HTML well before a 72 kB script.
- A real DevTools-throttled run (first pass) gives 1.45–1.48 s with Perf 100.
- With 9 runs the median falls in the slow mode on both routes. Six of nine runs on `/` and
  six of nine on the project page were slow.
- The 141 kB of JS is framework code only: there is no `"use client"` module in production.

**Levers tried, none closed it:**

- `browserslist`: Next 16.4 already defaults to the modern list, so no change. Reverted by
  the fix wave.
- `inlineCss`: worse, see the experiment above.
- Blocking the font: worse, 1804–2190 ms in the first pass.

**Recommendations (no code changed):**

1. **Accept the miss for M1 in writing, and re-measure on the Vercel preview in M3**
   (R15, R13). Use PageSpeed Insights or Lighthouse against the preview URL, which has a real
   CDN and TLS, and real-user LCP from Speed Insights. The budget is meant for the visitor's
   experience, and the localhost race inflates it in a way production does not. This is the
   cheapest honest resolution.
2. **If it must pass locally**, the only lever that remains is less JS before first paint.
   The page is fully static and has no client component, so the JS exists only for the router
   and RSC. Try these one at a time, with 9-run medians each, and with the owner's approval
   because they touch framework config:
   - `partialPrefetching: false`, and `prefetch={false}` on the above-the-fold `<Link>`s.
     This removes the RSC prefetch at about 620 ms, though not react-dom.
   - Check whether `cacheComponents` adds client runtime to these static routes.

   Expected gain is uncertain. Neither removes the 118 kB react-dom and router floor.

3. **Do not try** `display: 'optional'` or dropping the Inter preload. Blocking the font made
   LCP worse.
