# M1 metrics: core site

Measured 2026-10-24 on branch `m1-core-site` (HEAD `eaa7525`), against the shared production
build at `http://localhost:3300` (`next start`, Next.js 16.4.3, Turbopack). Budgets from the
spec §9. This is the first milestone, so there is no previous report to compare against.

**Caveat: fixture build.** This build had `CONTENT_FIXTURES=1`, so the home grid shows two
cards (`portfolio` and the test-only `long-content-fixture`). Production will show one card.
The fixture card sits below the fold and doesn't change the LCP element or the JS. The home
page numbers should hold for production, but this caveat stays until a non-fixture build is
measured.

**Method.** Lighthouse 12 CLI, headless Chrome. Mobile uses the default simulated throttling
(Lantern), with 6 runs per route; the table shows the median. Desktop uses
`--preset=desktop` at its real 1350×940 emulation, with 3 runs per route. The skill's
`--screenEmulation.disabled` flag was dropped because it made "desktop" render at the

`e2e/a11y.spec.ts` and `e2e/js-budget.spec.ts`, pointed at :3300 with a throwaway config in
`.metrics/`. `npm run e2e` ran last, on its own build on :3100.

## Misses

### 1. Mobile LCP 2338 ms on `/` and 1955 ms on `/projects/portfolio` (budget 1800 ms). Must fix

**Cause.** The simulated LCP is bimodal. It comes out at either about 1655 ms or about
2340 ms, and nothing about the page changes between runs. The difference is whether the
framework JS runs before the first paint:

- In the slow runs, the main-thread tasks before the observed paint include the evaluation
  of `/_next/static/chunks/20box33a0_n53.js` (react-dom, 71.9 kB gzip, 115 ms of scripting
  at 4× CPU in `bootup-time`). In `home-mobile-r3`, that is 4 tasks and 45 ms before LCP. In
  `home-mobile-r1`, it is 1 task and 14 ms.
- When those tasks come before the paint, Lantern puts the download and the 4×-throttled
  execution of react-dom and the app-router chunk (`3l_qmp-61z4yc.js`, 46.5 kB gzip) on the
  LCP path. That adds about 690 ms.
- With all `_next/static/chunks/*.js` blocked, LCP stays at 1578–1655 ms in all 3 runs. The
  no-JS floor passes; the JS is what tips it over.
- Neither LCP element is an image (both are text, see below), so this is not an image or
  priority problem.
- Blocking the Inter woff2 (48 kB, the only high-priority request besides the CSS) made FCP
  and LCP worse, at 1804–2190 ms. The font is not the lever.

**Evidence.** `.metrics/lh-*-mobile-r*.json`, audits `main-thread-tasks`, `bootup-time`,
`lcp-breakdown-insight` and `network-requests`. Counterfactual runs are in
`.metrics/cf-nojs-home-*.json` and `.metrics/cf-nofont-home-*.json`.

The 141 kB of JS is almost all framework: react-dom plus the Next router. Production has no
`"use client"` module (`app/ui/web-vitals.tsx` is dev-only). There is no app code to cut.

**Fixes, ranked by impact:**

1. **Drop the legacy polyfills.** Lighthouse `legacy-javascript-insight` reports 14 KiB in
   `20box33a0_n53.js`: `Array.prototype.at`, `flat`, `flatMap`, `Object.fromEntries`,
   `Object.hasOwn`, `String.prototype.trimStart` and `trimEnd`. Set a modern `browserslist`
   in `package.json` (for example `"browserslist": ["chrome 111", "edge 111", "firefox 111",
"safari 16.4"]`, Next's own modern baseline). That cuts the bytes on the critical path.
   This is a framework or config change, so it needs Yoav's approval first.
2. **Re-measure with the median of 9 or more runs, or accept the miss in writing.** The
   cross-check with real DevTools throttling gives 1.45–1.48 s with Perf 100 on both
   routes. Real visitors over the network get HTML long before the 72 kB react-dom chunk,
   so the slow mode is mostly a lab-model artefact of serving everything from localhost in
   under 35 ms. Under the skill's method it is still a miss. Either fix 1 brings the median
   under 1.8 s, or Yoav accepts the miss, and the reason goes in this report.
3. **Ask Next to do less before paint (worth trying).** Prefer anything that keeps the
   router from evaluating before the first frame, such as fewer above-the-fold `<Link>`
   prefetches. Lighthouse shows an RSC prefetch (`/?_rsc=…`) at about 620 ms. Measure
   before keeping any such change.

### 2. SEO 91 on `/`, mobile and desktop (budget 100). Must fix, trivial now

The one failing audit is **`meta-description`** ("Document does not have a meta
description"). `app/layout.tsx:8-10` exports a `metadata` with only `title`. The project
page sets `description: project.summary` (`app/projects/[slug]/page.tsx:24`) and scores 100. Fix it now rather than tracking it to M3: add
`description: site.hero.lead` (`app/lib/site.ts:29`) to the root metadata, or use a
dedicated `site.description` field.

No other SEO audit fails on either route. These pass already: `document-title`,
`http-status-code`, `is-crawlable`, `link-text`, `crawlable-anchors`, `image-alt`,
`hreflang`, `canonical` (not applicable without a canonical tag) and `robots-txt` (not
applicable on localhost). Open Graph, `sitemap.xml`, JSON-LD and the canonical URL are not
scored by Lighthouse SEO. They stay tracked to M3 (R11, R12) and are not M1 misses.

## The two questions

### 1. LCP element per route and form factor

| Route                 | Mobile (simulated)                            | Desktop (1350×940)      | Mobile (DevTools throttling, cross-check) |
| --------------------- | --------------------------------------------- | ----------------------- | ----------------------------------------- |
| `/`                   | `h1.mt-3` hero headline                       | `h1.mt-3` hero headline | `h1.mt-3`                                 |
| `/projects/portfolio` | `header.max-w-narrow > p.mt-5` lead paragraph | `p.mt-5` lead paragraph | **cover `img.h-auto`**                    |

On `/projects/portfolio`, the cover is the largest element in view on both form factors:

- Mobile: 372×233 at top 558 of an 823 px viewport, against 372×73 for the paragraph.
- Desktop: 1072×670 at top 577 of 940, against 704×61.

It still loses LCP in the standard runs because the current `cover.png` is a flat
placeholder. Next serves it as 843–912 B for 750–1200 px wide, about 0.01 bits per pixel.
Chrome ignores images under 0.05 bpp as low-content LCP candidates. With a real screenshot,
the cover will be the LCP element on desktop and, by area, on mobile too. Under DevTools
throttling it already is on mobile.

**Does `fetchPriority="high"` hurt?** Not measurably now. The cover request goes out as
High at 6–8 ms, right next to the CSS and the font. It is under 1 kB, and both routes reach
LCP at the same time whether or not the cover counts. The cheap "block the cover" run
didn't help: the blocked `<img>` became the LCP itself (`.metrics/cf-nocover-project-*`).
I did not rebuild without the attribute, to keep the shared build intact.

**Recommendation:** keep `loading="eager"` + `fetchPriority="high"`. The cover will be the
LCP once a real image lands. When it does, re-measure: a 100+ kB High-priority image
competes with the 48 kB Inter font and the CSS on mobile. If the paragraph is still the
mobile LCP then, drop `fetchPriority` but keep `loading="eager"`, and let `priority`
come only from desktop.

### 2. SEO caveats

Only `meta-description` on `/` fails, and it is trivially fixable now (see miss 2).
Nothing else needs to wait for M3 in order to score 100.

## Logs and other findings

- **5xx: no evidence of any, but no request log either.** `.metrics/server.log` holds only
  the 5 startup lines, with no warnings or errors. `next start` doesn't log requests, so
  "0 5xx" rests on:
  - every Lighthouse run getting 200 (and 404 for the not-found route),
  - the status assertions in the e2e specs,
  - 0 errors in the log.
    **Worth doing:** add a `page.on('response')` check for `status() >= 500` to
    `e2e/fixtures.ts`, so a 5xx fails a test the same way a console error does.
- `.metrics/build.log` and the e2e build have no warnings. All routes are static (`○`),
  with revalidate set to 30 days.
- **Worth doing:** `unused-javascript` flags 28 KiB of `20box33a0_n53.js` (react-dom). This
  is not actionable in app code. It is the same chunk as in miss 1.
- `render-blocking-insight`: the single 6.8 kB CSS file (`2ekql8hy_i_rh.css`) costs about
  120–150 ms of simulated mobile time. That is expected for one stylesheet, and Next can
  inline it (`experimental.inlineCss`), which is a config change. Worth trying only if fix
  1 isn't enough.
- **Shared build note:** `npm run e2e` rebuilt `.next` (same `CONTENT_FIXTURES=1`) while
  :3300 kept running. :3300 still answered 200 afterwards. The DevTools-throttling
  cross-check ran after that rebuild; every number in the table was measured before it.

## Method notes for the kit

- The skill's desktop command (`--preset=desktop --screenEmulation.disabled`) renders at
  the headless window's 756 px width, so it is not a desktop layout. Use `--preset=desktop`
  alone. Proposed change to `.claude/skills/metrics/SKILL.md`. I did not edit the skill.
- The Lantern LCP on a fast localhost is bimodal (about 1.65 s or about 2.34 s), so a
  single run is not enough to judge a 1.8 s budget. Use the median of at least 5 runs.
